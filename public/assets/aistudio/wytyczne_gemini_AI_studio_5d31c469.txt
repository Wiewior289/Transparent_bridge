### C. `PlcBridgeService.kt`: stan `STARTING` także musi blokować start

Oprócz zmian w UI proponuję zastąpić obecny warunek i początek `startBridge()` takim wzorcem. Wersja poniżej sprawdza też, czy urządzenie faktycznie udało się otworzyć, zamiast oznaczać mostek jako działający mimo braku adaptera:

```
import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.currentCoroutineContext
import kotlinx.coroutines.ensureActive

private var startJob: Job? = null

@Synchronized
fun startBridge(device: UsbDevice? = null) {
    if (_bridgeState.value == BridgeState.RUNNING ||
        _bridgeState.value == BridgeState.STARTING
    ) {
        Log.i(TAG, "Ignoring duplicate start: ${_bridgeState.value}")
        return
    }

    _bridgeState.value = BridgeState.STARTING

    startJob = serviceScope.launch {
        try {
            val targetDevice = device
                ?: usbManager.getFirstEthernetDevice()
                ?: throw IllegalStateException("No USB Ethernet device found")

            if (!usbManager.connectToDevice(targetDevice)) {
                throw IllegalStateException(
                    "Failed to connect USB device: ${targetDevice.deviceName}"
                )
            }

            currentCoroutineContext().ensureActive()

            val config = tailscaleManager.config.value

            tailscaleManager.startSubnetRouter(
                config.authKey,
                config.nodeName,
                config.advertisedRoutes
            )

            currentCoroutineContext().ensureActive()

            if (!tailscaleManager.config.value.isSubnetRoutingActive) {
                throw IllegalStateException(
                    "Tailscale backend did not start successfully"
                )
            }

            startRxLoop()
            startStatsLoop()

            _bridgeState.value = BridgeState.RUNNING

            logPacket(
                "SYS",
                "0.0.0.0",
                ethernetConfig.targetPlcIp,
                0,
                "Bridge Started",
                "",
                false
            )

            sendGratuitousArp()
        } catch (e: CancellationException) {
            usbManager.disconnect()
            tailscaleManager.stopSubnetRouter()
            throw e
        } catch (e: Exception) {
            Log.e(TAG, "Bridge startup failed", e)

            rxJob?.cancel()
            statsJob?.cancel()
            usbManager.disconnect()
            tailscaleManager.stopSubnetRouter()

            _bridgeState.value = BridgeState.ERROR
        }
    }
}
```

A do `stopBridge()` dodaj anulowanie inicjalizacji:

```

    startJob?.cancel()
    startJob = null

    rxJob?.cancel()
    statsJob?.cancel()

    usbManager.disconnect()
    tailscaleManager.stopSubnetRouter()

    _bridgeState.value = BridgeState.STOPPED

`ensureActive()` jest tu istotne: samo `cancel()` nie gwarantuje, że kod wykonujący synchroniczną operację USB albo JNI natychmiast się zatrzyma. Po powrocie z takiej operacji korutyna sprawdza, czy nadal wolno jej kontynuować.

Jeśli ekran Tailscale ma mieć osobny tryb startu, niech będzie to świadoma, serializowana operacja. Jeśli ma uruchamiać cały mostek, powinien korzystać z tej samej ścieżki startowej zamiast osobno uruchamiać backend.

### Problem 1: callback Go → Kotlin nie jest podłączony

W `bridge.go` funkcja `callJavaPacketCallback()` od razu wraca, jeśli `g_jniListener` albo `g_onPacketMethod` są puste. Odbiorca powinien udostępniać metodę zgodną dokładnie z sygnaturą JNI `([BI)V`:

### Problem 2: błędny wskaźnik do danych pakietu

W `UserlandTun.Write()` jest:

```

    (*C.uint8_t)(unsafe.Pointer(&packetData)),
    C.int(len(packetData)),
)
```

`&packetData` wskazuje na nagłówek Go slice, a nie na początek zawartości pakietu. Slice przechowuje wskaźnik, długość i pojemność. C interpretuje przekazaną lokalizację jako ciąg bajtów pakietu, więc odczytuje niewłaściwą pamięć.

Poprawka:

```

+    (*C.uint8_t)(unsafe.Pointer(unsafe.SliceData(packetData))),

Warunek `len(packetData) > 0` już istnieje, więc `unsafe.SliceData()` nie jest tu wywoływane dla pustego pakietu. W `go.mod` projekt ma Go 1.23, a więc ta funkcja jest dostępna.&#x20;

### Problem 6: brak walidacji długości pakietu w JNI

W `injectPacket()` kod robi:

```
length := int(jLen)
goBytes := make([]byte, length)
...
C.memcpy(unsafe.Pointer(&goBytes[0]), unsafe.Pointer(cBytes), C.size_t(length))
```

Jeśli `jLen == 0`, odwołanie do `goBytes[0]` powoduje panikę. Jeśli długość przekracza rozmiar `jPacket`, kopiowanie może odczytywać poza granicą tablicy.

Dodaj wrapper dla `GetArrayLength`:

```
static jsize jniGetByteArrayLength(JNIEnv* env, jbyteArray array) {
    return (*env)->GetArrayLength(env, array);
}
```

I walidację przed alokacją i kopiowaniem:

```
length := int(jLen)
arrayLen := int(C.jniGetByteArrayLength(env, jPacket))

if length <= 0 || length > arrayLen {
    return -2
}

goBytes := make([]byte, length)
```

Na koniec jeszcze dwie rzeczy: `jDataDir` trafia do `startTsnet()`, ale w `bridge.go` jest ignorowany, bo stan tworzysz przez `mem.Store`. To oznacza, że zachowanie nie odpowiada logom sugerującym użycie katalogu danych. Dodatkowo `getAssignedTailnetIp()` zwraca sfabrykowane `100.64.0.1`, gdy faktyczny adres nie jest dostępny. Taki fallback powinien zostać usunięty, bo może oznaczyć niepołączony backend jako działający.

## 6. Kolejność wdrożenia

Nie robiłbym wszystkich zmian jednocześnie. W pierwszej kolejności:

1. Ujednolicić start i stop w Kotlinie oraz zastosować blokadę i idempotencję w `UsbEthernetManager`.
2. Wybrać jeden domyślny tor VPN i przestać wstrzykiwać te same odpowiedzi do `PlcVpnService` i Go.
3. Naprawić `bridge.go`: rejestrację callbacku JNI, wskaźnik do danych pakietu, zdarzenie `EventUp`, konfigurację `wgengine` i synchronizację globalnego stanu.
4. Dopiero wtedy budować i testować: jeden start powinien dawać jedno otwarcie urządzenia USB, jeden aktywny backend Go, jeden tor pakietów powrotnych i czytelny błąd, jeśli którakolwiek faza inicjalizacji zawiedzie.
